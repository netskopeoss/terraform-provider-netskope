# BUG-012: List Data Source Returns `private_app_id = 0` for All Apps

**Resource:** `netskope_npa_private_apps_list` (data source)
**Severity:** High (all app IDs are missing — blocks import workflows and cross-resource references)
**Status:** Fixed (0.4.4) — Option C (hook)
**Affected attributes:** `private_app_id`

---

## Summary

The `netskope_npa_private_apps_list` data source returns `private_app_id = 0` for every private app. The real `app_id` values are present in the API response but are mapped to the wrong SDK struct field, so they never reach the Terraform schema.

This blocks any workflow that needs to discover app IDs programmatically — including `terraform import`, cross-resource reference resolution, and backup/restore operations.

## Symptoms

```hcl
data "netskope_npa_private_apps_list" "all" {}

output "app_ids" {
  value = [
    for app in data.netskope_npa_private_apps_list.all.private_apps : {
      name = app.private_app_name
      id   = app.private_app_id
    }
  ]
}
```

```
app_ids = [
  { id = 0, name = "Database Cluster" },
  { id = 0, name = "Internal Web Portal" },
  { id = 0, name = "SSH Application1" },
  # ... all IDs are 0
]
```

## Reproduction

1. Have one or more private apps on the tenant
2. Read the list data source
3. Observe `private_app_id = 0` for every app

Tested against tenant `bespin` on 2026-05-14. All 13 apps returned `private_app_id = 0`.

## Root Cause

The `PrivateAppsItem` SDK struct has **two ID fields** that map from different JSON keys:

**File:** `internal/sdk/models/shared/privateappsitem.go` (lines 64, 73)

```go
type PrivateAppsItem struct {
    AppID        *int    `json:"app_id,omitempty"`    // line 64 — maps from API's "app_id"
    PrivateAppID *int    `json:"id,omitempty"`        // line 73 — maps from API's "id"
    // ...
}
```

The **list API** (`GET /api/v2/steering/apps/private`) returns `app_id` in each item:

```json
{
  "data": {
    "private_apps": [
      {
        "app_id": 6802,
        "app_name": "[Database Cluster]",
        ...
      }
    ]
  }
}
```

But the **data source SDK mapping** reads from the wrong field:

**File:** `internal/provider/npaprivateappslist_data_source_sdk.go` (line 48)

```go
privateApps.PrivateAppID = types.Int32PointerValue(
    typeconvert.IntPointerToInt32Pointer(privateAppsItem.PrivateAppID))
//                                      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                                      This reads from JSON "id" — which
//                                      does NOT exist in the list response.
//                                      Should read from privateAppsItem.AppID
//                                      (JSON "app_id") instead.
```

The mapping uses `PrivateAppID` (json: `"id"`), but the list endpoint returns `"app_id"`, not `"id"`. Since `"id"` is absent from the list response, `PrivateAppID` deserializes as `nil` and defaults to `0`.

Meanwhile, `AppID` (json: `"app_id"`) correctly deserializes to `6802`, but is **never read** by the data source mapping code.

## Why This Exists

This is a consequence of KNOWN_API_ISSUES #2 and #6 — the Netskope API uses inconsistent field names across endpoints:

| Endpoint | ID Field | Name Field |
|----------|----------|------------|
| List apps (`GET /steering/apps/private`) | `app_id` | `app_name` |
| Single app (`GET /steering/apps/private/{id}`) | `app_id` | `name` |
| Create app (`POST /steering/apps/private`) | response `id` | `app_name` |

The SDK struct tries to handle all three by having both `AppID` (json: `app_id`) and `PrivateAppID` (json: `id`). Speakeasy's codegen mapped the Terraform schema's `private_app_id` to `PrivateAppID` (the `id` variant), which works for the single-app and create responses but fails for the list response.

## Fix Options

### Option A: Fix in data source SDK mapping (minimal change)

**File:** `internal/provider/npaprivateappslist_data_source_sdk.go` (line 48)

Change:
```go
privateApps.PrivateAppID = types.Int32PointerValue(
    typeconvert.IntPointerToInt32Pointer(privateAppsItem.PrivateAppID))
```

To:
```go
privateApps.PrivateAppID = types.Int32PointerValue(
    typeconvert.IntPointerToInt32Pointer(privateAppsItem.AppID))
```

**Risk:** This file is auto-generated by Speakeasy. The fix would be overwritten on next `speakeasy run` unless the file is added to `.genignore` or the fix is applied upstream in the OAS.

### Option B: Fix in OAS (preferred — survives regeneration)

Update the list response schema in the OAS to use `x-speakeasy-name-override` to map `app_id` to the same Terraform attribute as `id`, or unify the field names across endpoints.

### Option C: Fix via AfterSuccess hook (consistent with existing patterns)

Add logic to `hookMyBulkAppAfterSuccess.go` to copy `app_id` → `id` in the list response, similar to how `transport` → `type` is handled for protocols:

```go
// In the bulk app response loop:
if appData["app_id"] != nil && appData["id"] == nil {
    appData["id"] = appData["app_id"]
}
```

This approach is consistent with the existing hook-based normalization pattern and survives Speakeasy regeneration.

## Impact

- **Backup workflow:** Cannot discover app IDs from the list data source to generate `import` blocks
- **Cross-resource references:** Cannot build publisher → app or rule → app mappings using list data
- **Import automation:** Must fall back to raw API calls to discover IDs
- **tenant-ops module:** The backup mode relies on ID discovery for the import-to-state workflow

## Workaround

Query the API directly to get real `app_id` values:

```
GET /api/v2/steering/apps/private
```

Parse `app_id` from the response body. The data source correctly returns all other fields (name, hostname, protocols, publishers, tags).
