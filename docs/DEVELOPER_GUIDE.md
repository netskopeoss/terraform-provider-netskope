## 1. What This Provider Is

A **Terraform provider** is a plugin that lets Terraform manage resources on a third-party platform — in this case the Netskope REST API. Users write HCL configuration files like:

```hcl
resource "netskope_npa_private_app" "my_app" {
  private_app_name     = "Sales Portal"
  private_app_hostname = "sales.internal"
  protocols = [{ port = "443", protocol = "tcp" }]
  publishers = [{ publisher_id = "405", publisher_name = "us-west" }]
}
```

Terraform calls the provider (a compiled Go binary) to translate that config into API calls. The provider handles CRUD operations for each resource type and stores the resulting state in a `terraform.tfstate` JSON file.

This provider manages ~35 resources and ~50 data sources across NPA (private apps, publishers, rules), GRE/IPSec tunnels, URL lists, device classification, RBAC, and AI Gateway.

## 2. Development Process — The OAS-First Pipeline

### The Key Rule

> **You almost never edit Go files directly.**
> The Go source (except hooks) is generated by a tool called Speakeasy from OpenAPI Specification (OAS) YAML files. Editing generated files is overwritten on the next `speakeasy run`. The correct fix path is:
>
> 1. Fix the OAS file → regenerate → commit
> 2. Or write/edit a hook in `internal/sdk/internal/hooks/` → commit
>
> There is no option 3 (edit the generated Go directly) unless you add the file to `.genignore`.

### Where the OAS Files Live

The OAS files that drive generation live in a **separate repository**:

```
~/speakeasy/netskope-apiv2-oas/endpoints/
```

Each API domain has its own YAML file (e.g. `npa_private_apps.yaml`, `npa_rules.yaml`). The `.speakeasy/workflow.yaml` in this repo pulls them in during generation.

### The Generation Pipeline

```
OAS YAML files  ──speakeasy run──►  internal/sdk/         (SDK models + operations)
                                    internal/provider/     (Terraform resources + data sources)
                                    docs/                  (provider docs)
```

Running `speakeasy run` regenerates everything in `internal/sdk/` and `internal/provider/` (except files listed in `.genignore`). After every regeneration you must revert certain files that Speakeasy updates unnecessarily — see `docs/` memory for the revert list.

### Speakeasy Annotations on OAS Fields

Speakeasy reads special `x-speakeasy-*` extensions on OAS fields to control how Terraform schemas are generated:

| Annotation | Effect |
|---|---|
| `x-speakeasy-terraform-ignore: true` | Field is excluded from the Terraform schema entirely (invisible to users) |
| `x-speakeasy-ignore: true` | Field is excluded from the Go SDK struct (JSON deserializer skips it) |
| `x-speakeasy-param-suppress-computed-diff: true` | Generates a plan modifier that suppresses diffs for this computed field |
| `x-speakeasy-name-override: foo` | Renames the field in the generated Go struct |

These annotations are the primary tool for fixing drift and type-mismatch bugs without touching Go code.

## 3. How Terraform Works — End to End

This section explains what Terraform does, using Go terms. Think of Terraform as an orchestrator that calls into your Go binary at specific lifecycle points.

### 3.1 The Big Picture

```
terraform plan / apply
        │
        ▼
  Provider binary (Go) ──────────────────────────────────────────────────────┐
        │                                                                      │
  [Configure]          reads HCL config, builds SDK client with API key        │
        │                                                                      │
  [Schema]             declares every attribute name, type, computed/optional  │
        │                                                                      │
  For each resource:                                                           │
  [Read]               GET from API → update in-memory state                  │
  [ModifyPlan]         diff config vs state → optionally suppress false diffs  │
  [Create/Update/Delete] POST/PUT/DELETE → write new state                    │
        │                                                                      │
  Writes terraform.tfstate (JSON)                                             │
```

### 3.2 HCL → Go Struct

When a user runs `terraform plan`, Terraform parses their `.tf` files and deserializes the HCL values into Go structs using the `tfsdk` struct tags.

**Example:** the `NPAPrivateAppResourceModel` struct in `npaprivateapp_resource.go`:

```go
type NPAPrivateAppResourceModel struct {
    PrivateAppName   types.String         `tfsdk:"private_app_name"`
    PrivateAppID     types.Int32          `tfsdk:"private_app_id"`
    Protocols        []tfTypes.ProtocolItem `tfsdk:"protocols"`
    Publishers       []tfTypes.PublisherItem `tfsdk:"publishers"`
    // ...
}
```

The `tfsdk` tag tells the framework how HCL attribute names map to Go fields. Terraform's plugin framework handles all the HCL parsing; your code just receives a populated struct.

Note `types.String`, `types.Int32`, etc. — these are Terraform framework wrappers (not plain Go types) that track whether a value is null, unknown, or has a concrete value. Use `.ValueString()`, `.IsNull()`, `.IsUnknown()` to work with them.

### 3.3 The Resource Interface

Every resource must implement this interface:

```go
type Resource interface {
    Metadata(ctx, req, resp)      // registers the resource type name
    Schema(ctx, req, resp)        // declares attributes
    Create(ctx, req, resp)
    Read(ctx, req, resp)
    Update(ctx, req, resp)
    Delete(ctx, req, resp)
}
```

Additionally most resources implement:
- `ResourceWithImportState` — adds `ImportState` for `terraform import`
- `ResourceWithModifyPlan` — adds `ModifyPlan` for drift suppression

### 3.4 The Plan Phase (`terraform plan`)

1. Terraform calls `Read` on every resource in state to get current live values.
2. Terraform diffs the result against the HCL config.
3. If a `ModifyPlan` method exists, Terraform calls it — this is where the provider can suppress false diffs (see Section 6).
4. Terraform shows the user a diff and exits (plan-only).

### 3.5 The Apply Phase (`terraform apply`)

1. Terraform calls `Read` again (fresh state).
2. For new resources: calls `Create`.
3. For changed resources: calls `Update`.
4. For removed resources: calls `Delete`.
5. Each CRUD method must end with `resp.State.Set(ctx, &data)` to write the new state.

### 3.6 Create — Detailed Flow

Looking at `npaprivateapp_resource.go:Create()`:

```
1. req.Plan.Get(ctx, &plan)            // HCL → types.Object
2. plan.As(ctx, &data, ...)            // types.Object → NPAPrivateAppResourceModel
3. data.ToSharedPrivateAppsRequest()   // ResourceModel → SDK request struct
4. r.client.NPAPrivateApp.CreateNPAPrivateApps(ctx, request)  // SDK → HTTP POST
   │                                                            │
   │  [BeforeRequest hooks run here]                            │
   │  [HTTP request sent to Netskope API]                       │
   │  [AfterSuccess hooks run on response]                      │
   └────────────────────────────────────────────────────────────┘
5. data.RefreshFromSharedPrivateAppsGetResponse(ctx, res)  // SDK response → ResourceModel
6. resp.State.Set(ctx, &data)          // ResourceModel → state file (JSON)
```

### 3.7 State File

The state file (`terraform.tfstate`) is JSON. After a create, the framework serializes the `data` struct back to JSON using the same `tfsdk` tags. On the next plan, Terraform deserializes it back to compare against the live API response.

**This is why drift matters:** if the API returns a value that differs from what was saved in state, Terraform thinks a change is needed.

### 3.8 The SDK Layer

The SDK lives in `internal/sdk/`. It is a thin HTTP client generated by Speakeasy. For each operation there is:

- An `operations/` model (request parameters: path params, headers)
- A `shared/` model (request/response body structs)
- A method on an SDK object (e.g. `client.NPAPrivateApp.CreateNPAPrivateApps`)

The SDK marshals the request struct to JSON, sends the HTTP request, unmarshals the response JSON to a response struct, and returns it to the resource. Hooks intercept at the HTTP level — see Section 5.

### Key File: `*_resource_sdk.go`

This file contains two categories of functions:

**`ToShared*()`** — converts the Terraform resource model to SDK request structs:
```go
func (r *NPAPrivateAppResourceModel) ToSharedPrivateAppsRequest(ctx context.Context) (*shared.PrivateAppsRequest, diag.Diagnostics) {
    // reads r.PrivateAppName.ValueString(), r.Protocols, etc.
    // returns a *shared.PrivateAppsRequest ready for the SDK
}
```

**`RefreshFromShared*()`** — converts the SDK response back to the Terraform model:
```go
func (r *NPAPrivateAppResourceModel) RefreshFromSharedPrivateAppsGetResponse(ctx context.Context, resp *shared.PrivateAppsGetResponse) diag.Diagnostics {
    // reads resp.Data.PrivateAppName, resp.Data.Protocols, etc.
    // writes r.PrivateAppName = types.StringValue(...)
}
```

These are generated by Speakeasy. If a field is missing or has the wrong type in the SDK struct, the generated `RefreshFrom*` code will silently drop it or crash here.

## 5. Speakeasy SDK Hooks — The Break-Fix Safety Valve

### What Hooks Are

Hooks are middleware that intercept HTTP requests and responses at the SDK level. They are the **only manually maintained code** in `internal/sdk/` (everything else is generated). They give us a place to fix API quirks without modifying generated files.

### Hook Interfaces

Defined in `internal/sdk/internal/hooks/hooks.go`:

```go
type sdkInitHook interface {
    SDKInit(baseURL string, client HTTPClient) (string, HTTPClient)
    // Called once when the SDK is initialized. Used to wrap the HTTP client.
}

type beforeRequestHook interface {
    BeforeRequest(hookCtx BeforeRequestContext, req *http.Request) (*http.Request, error)
    // Called before each HTTP request is sent. Can modify the request body/headers.
}

type afterSuccessHook interface {
    AfterSuccess(hookCtx AfterSuccessContext, res *http.Response) (*http.Response, error)
    // Called after a 2xx response. Can modify the response body before the SDK deserializes it.
}

type afterErrorHook interface {
    AfterError(hookCtx AfterErrorContext, res *http.Response, err error) (*http.Response, error)
    // Called on network errors or non-2xx responses.
}
```

### How Hooks Know Which Operation They Are In

The `HookContext` embedded in every hook context carries `OperationID` — a string matching the Speakeasy `operationId` from the OAS (e.g. `"createNPAPrivateApps"`, `"updateNPARules"`). Every hook checks this first and returns `req, nil` or `res, nil` immediately if it doesn't apply:

```go
func (i *privateAppRequestHook) BeforeRequest(hookCtx BeforeRequestContext, req *http.Request) (*http.Request, error) {
    if hookCtx.OperationID != "updateNPAPrivateApp" {
        return req, nil   // not our operation, pass through
    }
    // ... transformation logic
}
```

### How Hooks Transform Data

Both BeforeRequest and AfterSuccess hooks follow the same pattern:

1. Read the body: `io.ReadAll(req.Body)` or `io.ReadAll(res.Body)`
2. Unmarshal into a local struct or `map[string]interface{}`
3. Make the transformation
4. Re-marshal back to JSON
5. Replace the body: `req.Body = io.NopCloser(strings.NewReader(modifiedBody))`
6. Update `ContentLength`: `req.ContentLength = int64(len(modifiedBody))`

This read-modify-write cycle means hooks work on the raw bytes, independent of what the SDK struct thinks the shape is.

### Hook Registration

`internal/sdk/internal/hooks/registration.go` is the central registry. It is the first file to look at when understanding which hooks are active:

```go
func initHooks(h *Hooks) {
    ruleRetry := &ruleCreateRetryHook{}
    h.registerSDKInitHook(ruleRetry)             // wraps HTTP client for retry

    ruleSerializer := &ruleCreateSerializer{}
    h.registerBeforeRequestHook(ruleSerializer)  // mutex before request
    h.registerAfterSuccessHook(ruleSerializer)   // releases mutex after response
    h.registerAfterErrorHook(ruleSerializer)     // releases mutex on error

    errorStatus := &errorStatusResponse{}
    h.registerAfterSuccessHook(errorStatus)      // converts 200+error→error

    MyApp := &myAppResponse{}
    h.registerAfterSuccessHook(MyApp)            // private app response transforms

    MyPolicyRequest := &myPolicyRequest{}
    h.registerBeforeRequestHook(MyPolicyRequest) // rule request transforms

    privateAppReq := &privateAppRequestHook{}
    h.registerBeforeRequestHook(privateAppReq)   // strips empty fields from PUT

    // ... more hooks
}
```

Hooks run **in registration order** within each phase. The ordering matters: e.g. `errorStatusResponse` must run before `myAppResponse` so a soft 404 is caught before the SDK tries to deserialize an error body as a real app.

## 6. State Drift — What It Is and Why It Happens

### What Drift Is

**Drift** (or a "perpetual diff") happens when `terraform plan` shows changes even though the user has not modified their HCL config. On every plan, Terraform runs `Read` to get the live API state, then diffs it against the stored state. If the API consistently returns something different from what was stored, Terraform proposes a change on every single plan — even though applying it would not actually fix anything.

For users this is disruptive: their CI pipelines fail, they get confused `apply` outputs with no real effect, and they can't tell real drift from phantom drift.

### Why the Netskope API Causes Drift

The Netskope API has several behaviors that create drift:

**1. Non-deterministic ordering.** The API returns lists (publishers, protocols, tags) in different orders on each response. Terraform lists are order-sensitive — `["a", "b"]` ≠ `["b", "a"]`. Every plan shows a reorder.

**2. Field name inconsistency.** The API uses `transport` in GET responses but expects `type` in POST/PUT. If the state stores `type` but the API returns `transport`, every Read sees a mismatch.

**3. Write-only fields.** Some fields are accepted on create/update but never returned by GET (e.g. `group_id` on NPA rules). If the state stores the value but the API returns nothing, the next Read sets the field to null — causing a perpetual "add" diff.

**4. Computed fields without plan modifiers.** Some fields (e.g. `group_name`) are returned by the API but only sometimes — not on every endpoint. If the schema marks them `Computed: true` without `UseStateForUnknown`, Terraform shows `(known after apply)` on every plan, which counts as a change.

**5. Format normalization.** The API modifies data on write: app names get wrapped in `[]`, hostnames get whitespace normalized around commas, protocol ports get reordered. The stored state has the raw user value; the next Read returns the normalized version.

**6. Display name vs file name.** Block rule templates are sent with display names ("Default Template") but returned with file names ("23.html"). Every Read sees a mismatch.

### How We Fix Drift

There are four tools:

**Tool 1: Sort in AfterSuccess hooks.**
Sort lists before the SDK deserializes the response, so the state always stores a canonical order regardless of what the API returned.

**Tool 2: OAS annotations.**
- `x-speakeasy-terraform-ignore: true` — remove the field from the schema entirely. No field = no drift. Use when the API returns a field that the user cannot or should not set.
- `x-speakeasy-param-suppress-computed-diff: true` — generates `UseStateForUnknown` plan modifier. Tells Terraform "if we don't know the new value yet, keep the state value" — eliminates `(known after apply)` perpetual diffs.

**Tool 3: Plan modifiers in `*_resource_planmodify.go`.**
Custom `ModifyPlan` implementations that compare plan vs state and suppress false diffs. Example: if plan and state contain the same set of publishers but in different order, write the state order into the plan so Terraform sees no diff.

**Tool 4: BeforeRequest hooks.**
Strip or transform request payloads to prevent the API from normalizing values in a way that would cause drift on the next Read. Example: strip `.html` block rule template filenames from update payloads so the API doesn't re-normalize them.

## 7. Issues Since March 2026 — Bugs vs Features

The table below covers all changes from v0.4.0 (released 2026-03-31) onwards, categorized as:

- **True bug** — something that worked in a prior version stopped working, or a field behaved incorrectly
- **API change** — the Netskope API changed its behaviour, breaking the provider
- **Feature** — new resource, data source, or capability

### True Bugs (Break-Fix Relevant)

| Version | Issue | Root Cause Category | Fix Mechanism |
|---|---|---|---|
| 0.4.0 | `bypass_uris` SQL error on private app update | API rejects empty arrays | BeforeRequest hook |
| 0.4.0 | `emit_alert`/`template` silently stripped from block rules | Hook struct missing fields | Added fields to hook struct |
| 0.4.0 | `device_classification_id` type mismatch (string↔int) | API returns strings, expects ints | OAS (`string`) + BeforeRequest hook (coerce to int) |

| 0.4.4 | `private_app_id = 0` in list data source | List endpoint uses `app_id`, SDK reads `id` | AfterSuccess hook copies `app_id`→`id` |
| 0.4.4 | `pop_names` and `options` missing from GRE/IPSec tunnel list | Fields excluded by `terraform-ignore` annotation | OAS fix + regenerate |

| 0.4.9 | Hook structs missing `notify`, `schedule`, `periodic_reauth` fields | Hook model not updated when OAS added new fields | Added missing fields to hook structs |

### Count

From v0.4.0 through v0.4.10: **~16 true bugs fixed**, **1 API change** (publisher connected_apps). The remaining changes in each version are new features.

### Pattern Analysis

Looking across all the bugs, three patterns repeat:

**Pattern A — Hook struct out of sync with OAS.**
When a new field is added to the OAS and regenerated into the SDK, the hooks that intercept that operation still have old local structs that don't know about the new field. The JSON unmarshal silently drops the field (it goes to zero value), which then gets re-marshalled into the request/response with an empty or missing value. BUG-018 (classification type) and the missing `notify`/`schedule` fields in v0.4.9 are both this pattern. **Fix:** update the hook struct to match the OAS model.

**Pattern B — API response shape diverges from what the OAS says.**
The API changes what it returns without updating documentation. BUG-017 (publisher connected_apps changed from strings to objects) is the clearest example. The SDK struct was declared as `[]string` and crashed when the API started returning objects. **Fix:** use `x-speakeasy-ignore` to exclude the field from deserialization, or change the OAS type and regenerate.

**Pattern C — Field excluded from the wrong schema direction.**
Some fields should be excluded from the response schema (to preserve user-set state) but were not, or should be included in the response schema but were wrongly excluded (BUG-014, BUG-015, BUG-016). **Fix:** adjust the `x-speakeasy-terraform-ignore` annotation on the OAS response schema — not the request schema.

## Appendix — Worked Example: Publisher Ordering Drift

This worked example traces the complete lifecycle of a bug (BUG-001) from symptom to fix, showing exactly which files are involved and in what order.

### Symptom

A user has a private app with two publishers:

```hcl
resource "netskope_npa_private_app" "sales" {
  private_app_name = "Sales Portal"
  # ...
  publishers = [
    { publisher_id = "100", publisher_name = "us-west" },
    { publisher_id = "200", publisher_name = "us-east" },
  ]
}
```

Every `terraform plan` shows:

```
~ resource "netskope_npa_private_app" "sales" {
    ~ publishers = [
        ~ { publisher_id = "200", publisher_name = "us-east" },   # was index 1
        ~ { publisher_id = "100", publisher_name = "us-west" },   # was index 0
      ]
  }
```

Nothing actually needs to change — the same two publishers are assigned. But Terraform thinks they need reordering every time.

### Diagnosis

**Step 1: Identify the Read path.**

The symptom appears during `terraform plan`, which means it's in `Read`. Find the resource file:

```
internal/provider/npaprivateapp_resource.go → Read()
```

`Read` calls:
```go
r.client.GetNPAPrivateApp(ctx, request)
```

which hits `GET /api/v2/steering/apps/private/{id}`.

**Step 2: Check what the API actually returns.**

Enable debug logging or check `docs/KNOWN_API_ISSUES.md`. The API returns publishers in non-deterministic order — sometimes `[us-west, us-east]`, sometimes `[us-east, us-west]`.

**Step 3: Trace how the response reaches the state.**

```
HTTP response body (raw JSON)
    │
    ▼ AfterSuccess hooks fire (in registration order)
    │   hookErrorStatusResponse — checks for error, passes through
    │   hookMyAppAfterSuccess   — reads body, unmarshals, transforms, re-marshals
    ▼
SDK deserializes into shared.PrivateAppsGetResponse
    │
    ▼ data.RefreshFromSharedPrivateAppsGetResponse()
    │   (in npaprivateapp_resource_sdk.go)
    │   Iterates resp.Data.ServicePublisherAssignments → populates data.Publishers
    ▼
resp.State.Set(ctx, &data)
    │
    ▼ terraform.tfstate (JSON) — stores whatever order the API returned
```

**Step 4: Confirm the fix location.**

The hook `hookMyAppAfterSuccess.go` runs before the SDK deserializes. If we sort publishers there, the state will always store them in a consistent order, so the next Read also returns the same order — no diff.

### The Fix

In `internal/sdk/internal/hooks/hookMyAppAfterSuccess.go`, inside `AfterSuccess()`, after unmarshalling the response into `responseMap`:

```go
// Sort publishers by publisher_id to ensure deterministic ordering.
// The API returns publishers in non-deterministic order, which causes
// perpetual diffs because the schema uses ListNestedAttribute (order-sensitive).
sort.Slice(responseMap.Data.ServicePublisherAssignments, func(i, j int) bool {
    idI := fmt.Sprintf("%v", responseMap.Data.ServicePublisherAssignments[i].PublisherID)
    idJ := fmt.Sprintf("%v", responseMap.Data.ServicePublisherAssignments[j].PublisherID)
    numI, errI := strconv.Atoi(idI)
    numJ, errJ := strconv.Atoi(idJ)
    if errI == nil && errJ == nil {
        return numI < numJ
    }
    return idI < idJ
})
```

Also note: the API returns `publisher_id` as a float64 in JSON (e.g. `405.0`). The hook also normalizes this to a string before sorting:

```go
case float64:
    responseMap.Data.ServicePublisherAssignments[i].PublisherID = fmt.Sprintf("%.0f", v)
```

And trims whitespace from `publisher_name` (the API sometimes returns `" us-west"` with a leading space):

```go
responseMap.Data.ServicePublisherAssignments[i].PublisherName = strings.TrimSpace(...)
```

### Why No OAS Change Was Needed

The OAS correctly declares `publishers` as a list. The problem was purely in what the hook did (or didn't do) with the API response. No field type was wrong; the SDK deserialization was fine. Only the sort order was missing from the hook.

### File Touch List for This Fix

```
internal/sdk/internal/hooks/hookMyAppAfterSuccess.go      ← added sort + normalize
internal/sdk/internal/hooks/hookMyBulkAppAfterSuccess.go  ← same fix for list operations
internal/sdk/internal/hooks/hookMyAppAfterSuccess_test.go ← unit tests for sort logic
internal/provider/drift_detection_test.go                 ← acceptance test TestAccDrift_PrivateApp_MultiPublisherWithTags
```

Note: `registration.go` did not change — `myAppResponse` was already registered. No OAS changes. No resource file changes.

### Why the Hook, Not a Plan Modifier?

A plan modifier runs after `Read` and can suppress diffs between plan and state. But the drift here comes from Read writing an inconsistent order to state. If we only suppressed the diff in `ModifyPlan`, the state would accumulate inconsistency — the next plan after apply would show the same diff again. Fixing it in the hook ensures the state is written consistently from the start.

For comparison, config-order drift (BUG-002, where the user reorders publishers in their HCL) *is* handled in `ModifyPlan` — because there the API is consistent but the user changed their config order. The distinction:

- API returns inconsistent order → fix in AfterSuccess hook (canonicalize before state write)
- User writes inconsistent config order → fix in ModifyPlan (suppress diff if elements are the same set)
